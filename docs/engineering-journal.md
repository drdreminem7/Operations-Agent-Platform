# Engineering journal

This is the running account of what we actually built. The [plan](../production-ai-operations-agent-platform-plan.md) describes the destination; this journal describes the current implementation, the request flow, verification, and what you should be able to teach someone else. Read it alongside the [learning guide](milestone-learning-guide.md). New milestones get an entry when their implementation is verified.

## Milestone 0 — Charter and boundaries

**Built:** A scoped incident-response agent plan, an architecture description, and a record of the initial scope decision. The first version uses a simulated operations environment. It is not authorized to change real production systems.

**Files:** `production-ai-operations-agent-platform-plan.md` is the long roadmap and success criteria. `README.md` is the project entry point and setup guide. `docs/architecture.md` describes the components and boundaries. `docs/adr/0001-initial-scope.md` records why this scope was chosen. `docs/learning-log.md` holds dated learning notes. None of these files executes a run; they are the contract against which the implementation is reviewed.

**Flow:** Incident arrives → application gathers evidence with named tools → a decision provider proposes an action → application policy and human approval control side effects → state and audit records explain what happened.

**Explain:** Why this is a stateful execution system rather than a chatbot; why the model may propose but not authorize; what is deliberately simulated; why an audit trail and explicit stop conditions matter.

## Milestone 1 — Runnable service and engineering baseline

**Built:** An installable FastAPI service, local PostgreSQL, health/readiness checks, Alembic, lint/type/test commands, and CI.

**Files:** `pyproject.toml` declares dependencies and tool settings; `uv.lock` pins the resolved environment. `docker-compose.yml` starts PostgreSQL and mounts its named data volume. `.env.example` documents local configuration; `.gitignore` keeps secrets and generated files out of Git. `src/app/database.py` builds the SQLAlchemy engine and declarative base. `src/app/main.py` creates FastAPI and mounts routes. `src/app/routes/health.py` implements `/health` and database-aware `/ready`. `tests/test_health.py` checks the endpoint contracts. `alembic.ini`, `migrations/env.py`, and `migrations/versions/` configure and version database changes. `.github/workflows/` repeats automated checks in CI.

**Flow:** Uvicorn imports `app.main:app` → a health request reaches the health router; readiness additionally opens a database connection → the API responds with live/ready or unavailable. `uv` resolves dependencies locally; CI runs checks after a push; Alembic applies migrations against PostgreSQL.

**Explain:** Image vs running container vs persistent named volume; host/container port mapping; liveness vs readiness; engine vs session; what CI verifies and cannot verify; why migrations are separate from Python model classes; why `.env` stays local.

## Milestone 2 — Incident API and schema

**Built:** PostgreSQL-backed incident create, list, get, and partial update endpoints, validation and response models, migrations, and an index on creation time.

**Files:** `src/app/models.py` defines the `Incident` ORM mapping, constraints, and index. `src/app/schemas.py` defines `IncidentCreate`, `IncidentUpdate`, and `IncidentResponse`. `src/app/routes/incidents.py` handles HTTP, sessions, persistence, and 404s. `src/app/main.py` mounts the router. `migrations/versions/a7e280eb7b1e_create_incidents_table.py` creates the table; `migrations/versions/b550434f6626_index_incidents_by_creation_time.py` adds the index. `migrations/env.py` connects model metadata to Alembic. `tests/test_incidents.py` exercises validation and database behavior.

**Flow:** Client JSON → Pydantic request schema → route → SQLAlchemy `Session` → `Incident` row → `commit()` persists → `refresh()` loads generated fields → response schema serializes JSON. For PATCH, `exclude_unset=True` distinguishes omitted fields from an explicit nullable `null` before assigning and committing.

**Explain:** ORM mapping vs applied migration vs API schema; primary key, nullability, defaults and index; 201, 404 and 422; transaction and refresh; why the planner may scan a tiny table even with an index; why titles are not unique.

## Milestone 3 — Bounded tool system

**Built:** A registry, executor, shared tool contract, and three simulated read tools. No arbitrary Python or shell command can be requested through this interface.

**Files:** `src/app/tools/base.py` defines the abstract async contract; `metadata.py` names tools and permissions; `result.py` standardizes outputs; `errors.py` defines controlled failures; `registry.py` resolves known names; `executor.py` checks permissions, validates inputs, enforces timeout and validates results; `defaults.py` assembles the registry. `service_health.py`, `search_logs.py`, and `recent_deployments.py` implement simulated data access; `__init__.py` marks the package. Tests mirror these boundaries: `tests/test_tool_contracts.py`, `test_tool_metadata.py`, `test_tool_registry.py`, `test_tool_executor.py`, `test_default_tools.py`, `test_service_health_tool.py`, `test_search_logs_tool.py`, and `test_recent_deployments_tool.py`.

**Flow:** Named request → registry lookup → permission check → input validation → timeout-bounded `async execute` → output validation → `ToolResult`. A failure stops the chain and becomes a controlled exception.

**Explain:** Abstract class, `@property`, metadata and registry; why permission checking differs from argument validation; why results are structured; why tool output is untrusted data, not instructions; what timeout does and does not guarantee.

## Milestone 4 — Deterministic run engine and persistence

**Built:** A finite-state run, legal transitions, a deterministic provider, database-backed run/step history, and run HTTP endpoints. Execution and verification were deliberately simulated at this stage.

**Files:** `src/app/agent/states.py` names states; `transitions.py` lists legal edges; `run.py` holds in-memory state/history; `decision_provider.py` validates decisions and provides deterministic choices; `provider.py` defines the provider interface; `engine.py` applies one step at a time; `repository.py` persists and reloads runs and steps. `src/app/models.py` adds `AgentRunRecord` and `RunStepRecord`; `schemas.py` adds their response shapes; `routes/runs.py` starts, steps, and reads runs; `main.py` mounts it. `migrations/versions/42f41ea0209a_add_agent_run_tables.py` creates the tables. `tests/test_agent_run.py`, `test_agent_transitions.py`, `test_decision_provider.py`, `test_decision_schemas.py`, `test_agent_engine.py`, `test_agent_repository.py`, `test_agent_engine_persistence.py`, `test_agent_execution_simulation.py`, and `test_runs.py` cover the state, persistence, simulation, and API boundaries. The initial `agent/action_policy.py` heuristic was replaced by Milestone 6's central policy engine.

**Flow:** Create incident → POST run → repository creates `agent_runs` row → POST step reloads the run and incident → engine obtains a deterministic decision or runs a read tool → transition table checks the edge → repository writes new state plus numbered `run_steps` row in one transaction → engine updates memory only after commit → API returns current state. Reload reconstructs evidence and proposal from saved steps.

**Explain:** State vs transition; why a step is persisted with state; why memory updates after a successful transaction; how reload reconstructs a run; how an illegal edge is rejected; why the simulated success is not evidence that a real rollback worked.

## Milestone 5 — Model provider boundary

**Built:** A switchable deterministic/Gemini decision provider, constrained wire-format responses, application-side decision validation, provider error mapping, and opt-in live verification.

**Files:** `src/app/agent/provider.py` is the async provider protocol. `decision_provider.py` contains strict `ToolRequest` and `ActionProposal` domain schemas and the deterministic implementation. `src/app/agent/providers/factory.py` selects the configured provider; `gemini.py` owns the Gemini request, response parsing, timing and token metadata; `errors.py` defines provider failure types; `__init__.py` marks the package. `src/app/agent/engine.py` awaits the selected provider and keeps transitions application-owned. `src/app/routes/runs.py` maps provider timeout/failure to HTTP 504/502. `.env.example` documents the selection/key variables. `tests/test_gemini_decision_provider.py`, `test_gemini_generator.py`, `test_provider_factory.py`, `test_gemini_live.py`, and additions to `test_runs.py` verify local boundaries and the opt-in network path.

**Flow:** Run engine calls provider protocol → factory-selected implementation chooses a named read tool or proposes a bounded action → Gemini returns structured output → domain schema and evidence checks reject malformed or unsupported proposals → engine, not the model, decides the next state and execution boundary.

**Explain:** Protocol vs implementation; provider wire schema vs domain validation; structural vs semantic vs authorization checks; why async network work, timeout and error translation matter; why prompts/responses and API keys are not logged; why deterministic mode is the CI default.

**Verification:** Offline suite, Ruff, mypy and Alembic checks passed in the previous implementation pass. The live Gemini request reached the API but failed with `API_KEY_INVALID`; a valid key is still needed to verify the live path. Do not describe that as a successful live integration.

## Milestone 6 — Policy and simulated write tools

**Built:** Server-owned permission levels and decisions (`ALLOW`, `REQUIRE_APPROVAL`, `DENY`), simulator-only restart and rollback tools, and shared simulator state for the health/deployment read tools. The old name-only approval heuristic was removed. The model only proposes bounded actions; it cannot set its own risk class or granted permissions.

**Files:** `src/app/policy.py` owns canonical tool-to-permission/risk rules, actor capabilities, the simulation-only guard, low-risk configuration, and decision reasons. `src/app/agent/engine.py` evaluates policy before reads, when selecting an action, when requesting approval, and before execution; proposal steps now record policy outcome/reason. `src/app/tools/simulator.py` stores synthetic health and deployment state. `src/app/tools/restart_service.py` and `rollback_deployment.py` validate and mutate that state; `service_health.py` and `recent_deployments.py` read it; `defaults.py` injects one simulator into the related tools. `src/app/tools/executor.py` still enforces permissions and validation at execution. `tests/test_policy_engine.py` covers read/write/unknown/forbidden/cross-service decisions; `tests/test_simulated_write_tools.py` checks permissions, stale versions, and state changes; `tests/test_default_tools.py` checks registry contents; `tests/test_agent_engine.py` checks state integration.

**Flow:** Provider proposes a named tool/action → application looks up its canonical rule → policy checks actor capabilities, incident service, risk level, and simulation context → read is allowed, write requires approval unless explicitly configured low-risk, unknown/administrative/real-environment writes are denied → executor independently checks permission and validates arguments → simulator returns a structured result.

**Explain:** Validation asks whether arguments have the right shape and meaning; authorization asks whether this actor may request the operation; approval is a human decision over a specific action; execution performs it. Explain why a model-supplied `risk=read` cannot lower server policy, why unknown tools are denied, and why a simulated write is not a production integration.

**Verification/limits at this stage:** Policy and simulator tests passed. The simulator was in process memory, and the write tools were not yet driven by run execution; Milestone 8 connects them. There is no enterprise identity system; the agent uses a fixed application actor for simulated runs.

## Milestone 7 — Durable human approval

**Built:** Pending/approve/deny endpoints; a PostgreSQL approval row that freezes run ID, tool, arguments, request/expiry time, and SHA-256 action hash; atomic approval request plus state transition; atomic decision plus audit step; single-use and expiry checks; and a hash recheck before execution. Approval endpoints require a configured shared API key and an operator ID header.

**Files:** `src/app/agent/approval.py` computes a canonical hash over run/tool/arguments. `src/app/models.py` maps the approval row and unique-per-run constraint; `migrations/versions/7f31d9c2a008_add_approvals.py` creates its table/index/constraints. `src/app/agent/repository.py` creates the approval in the same transaction as the waiting transition, locks rows when deciding, checks expiry/hash/state, and writes the decision and run step atomically. `src/app/agent/engine.py` uses that repository for persisted decisions and rechecks approval before the simulated execution step. `src/app/routes/approvals.py` protects and exposes the API; `src/app/schemas.py` defines the response; `src/app/main.py` mounts the route; `.env.example` names `APPROVAL_API_KEY`. `tests/test_approvals.py` exercises auth, pending review, approval, denial, replay, expiry, saved-action tampering, execution tampering, ended runs, and two simultaneous deciders. `tests/test_agent_engine_persistence.py` verifies the updated proposal audit payload.

**Flow:** Run enters `action_selected` → policy requires approval → one DB transaction writes `awaiting_approval`, a numbered run step, and the frozen approval row → operator GETs pending requests with the shared key → POST approve/deny locks the approval and run rows, verifies expiry, state and saved-action hash, then writes decision plus state/step in one transaction → execution recomputes the hash from the actual proposal and refuses a mismatch. Denial escalates; it never executes automatically.

**Explain:** Why hashing canonical JSON binds an approval to one run/tool/argument set; why it is not a digital signature; why row locking plus a unique constraint prevents double decisions; what a transaction makes atomic; why an expired or tampered approval returns 409; why a model cannot approve itself.

**Verification/limits at this stage:** PostgreSQL migration applied; full suite: 155 passed, 1 live Gemini test skipped; Ruff, mypy, and `alembic check` passed. The shared key is suitable for local development, not individual authenticated identities; `X-Operator-ID` is an audit label, not proof of identity. Approval lasts 15 minutes and has no renewal path. At Milestone 7, execution still recorded a simulated action without invoking the write tool; Milestone 8 connects it. Crash-safe side-effect delivery remains Milestone 9.

## Milestone 8 — Functional end-to-end incident response

**Built:** A deterministic bad-deployment scenario that gathers health, deployment, and log evidence; proposes a rollback; waits for an exact human approval; executes the rollback against a per-run simulator; verifies recovery; and marks both run and incident resolved. Failed execution or verification ends the run as failed rather than claiming success. Decision-call metadata is saved with audit steps.

**Files:** `src/app/agent/provider.py` extends the provider contract with prior evidence so repeated investigation choices can progress. `src/app/agent/decision_provider.py` chooses the three read tools in order for the combined latency/deployment scenario, requires supporting health/log evidence before deterministic rollback, and defines `DecisionTrace`. `src/app/agent/providers/gemini.py` receives prior evidence and attaches model/latency/token metadata to validated decisions. `src/app/agent/transitions.py` permits a bounded return to `gather_context`. `src/app/agent/engine.py` gathers each read result, uses the approved action's canonical policy permissions, executes the write tool, performs separate health/deployment verification, and records each result or failure. `src/app/tools/defaults.py` can build a registry around a supplied simulator; `src/app/tools/simulator.py`, `rollback_deployment.py`, `service_health.py`, and `recent_deployments.py` supply the synthetic effect and verification data. `src/app/routes/runs.py` gives each run an isolated executor/registry. `src/app/agent/repository.py` persists the audit steps, closes terminal runs with `finished_at`, and marks the incident resolved only after verification. `src/app/models.py` and `schemas.py` from earlier milestones remain the DB/API contracts; no new migration was needed. `tests/test_incident_response_e2e.py` covers the full HTTP flow and per-run isolation. `tests/test_agent_execution_simulation.py` covers execution, failed verification, and stale deployment. `tests/test_gemini_decision_provider.py` and `tests/test_agent_engine_persistence.py` check decision traces and persisted payloads. `docs/demo-v1.md` gives the manual walkthrough; `README.md` links to it.

**Flow through files:** POST `/incidents` → incident route/schema/model persists the incident → POST `/incidents/{id}/runs` → runs route/repository creates a run → seven POST step calls move through triage, three read-tool calls, planning, action selection, and awaiting approval → each decision comes from the provider contract, each tool passes policy and executor checks, and each transition is written by the repository → approvals route/repository freezes and approves the rollback → next step rechecks policy and the approval hash, then runs `rollback_deployment` in that run's simulator and records its `ToolResult` → final step reads health and deployments, records verification evidence, and updates run/incident in one database transaction. GET run/steps/incident exposes the result afterward.

**Explain:** Why collecting three different signals is stronger than treating a title as proof; why a model suggestion is not authorization; how the approval hash binds the tool and arguments; what the tool executor checks; why the application-owned verification read differs from trusting a tool's `status=rolled_back` response; why `resolved` is written only after evidence checks; what a provider trace reveals without retaining sensitive prompts; why per-run simulator isolation prevents one demonstration from contaminating another.

**Verification/limits:** Full suite: 162 passed, 1 opt-in live Gemini test skipped; Ruff and mypy pass, and no schema change was required. The demo is repeatable with the deterministic provider. The `v0.1.0` tag and a video recording remain undone because the worktree has uncommitted work and the live Gemini key has not been validated. The simulator is process-memory state: restarting after execution but before verification loses its effect. Tool execution and recording its result are not crash-atomic, and duplicate requests still need durable idempotency. Milestone 9 addresses those failure windows. This remains a simulated platform, not a real production operations integration.

## Milestone 9 — Fail-closed durable execution

**Built:** A unique PostgreSQL execution record is committed before an approved write. It stores the run-bound action hash as an idempotency key, exact tool and arguments, status, timestamps, and eventual result or error. A second request cannot start the same write while the first is in progress. An old `started` record is conservatively marked `uncertain` and the run fails without automatic retry. A successful tool result, execution status, run transition, and audit step are committed in one transaction. A fresh engine can reconstruct the local simulator from a previously saved successful result and continue verification. Each tool explicitly declares a retry class; unknown/custom tools default to no retry. No current write tool is classified as idempotent.

**Files:** `src/app/models.py` maps `ActionExecutionRecord` and its unique/check constraints; `migrations/versions/e4d8a9b6c201_add_action_executions.py` creates the table. `src/app/agent/repository.py` claims execution under a row lock, checks approval/action integrity, detects stale intent, records uncertain outcomes, and persists success with the state transition atomically. `src/app/agent/engine.py` claims before calling the write tool, never blindly repeats an unrecorded action, and uses repository methods to save the result. `src/app/tools/metadata.py` defines retry classes and rejects read/write mismatches; the three read tools and two write tools declare their classes in their respective files. `src/app/tools/simulator.py` rebuilds synthetic state from saved successful tool results. `src/app/routes/runs.py` creates that per-run executor and exposes the execution-inspection endpoint; `src/app/schemas.py` defines its response. `tests/test_tool_metadata.py` checks every default tool classification and the fail-closed custom default. `tests/test_agent_crash_recovery.py` injects the before-effect, after-effect/before-persist, persistence-failure, tool-error, and transaction-write-failure windows. `tests/test_incident_response_e2e.py` proves successful result recovery in a fresh engine and inspects the execution row. `docs/failure-model.md` lists the known crash windows and guarantees; `docs/demo-v1.md`, `docs/architecture.md`, `docs/milestone-learning-guide.md`, and `README.md` describe the current behavior.

**Workflow:** Approved run enters `executing` → engine rechecks approval/policy → repository locks the run and commits a unique `started` execution row → tool executor runs the simulated write → repository commits result, `succeeded`, `verify` state, and numbered step together → verification may resume from this record after a restart. If a request sees the still-fresh `started` record, it gets a conflict; if the record is older than 10 seconds, it becomes `uncertain`/`failed` and no second tool call occurs. A tool exception is also treated as potentially uncertain, not proof of no effect.

**Explain:** The difference between a committed intent and a committed result; why a database transaction cannot include an arbitrary remote side effect; how a unique run-bound key prevents duplicate local claims but does not provide global or provider-level deduplication; why timeout does not imply the operation failed; why a conservative uncertain state sacrifices availability for safety; how a successful simulated result can be replayed without repeating a real side effect; which database updates are atomic.

**Verification/limits at this stage:** PostgreSQL migration applied; 173 tests passed, 1 opt-in live Gemini test skipped; Ruff, mypy, and `alembic check` passed. Milestone 9 is complete for the simulated, fail-closed execution path, not a full external exactly-once or reconciliation system. Retry classes are policy metadata; they do not trigger automatic tool retries. At this stage there was no retry/backoff scheduler, external provider idempotency, cross-run deduplication, manual confirmation endpoint, or background worker; Milestone 10 adds bounded job/decision retries and a worker. An uncertain real-world outcome still requires an operator and an external system-of-record check. The local shared approval key is not enterprise authentication.

## Milestone 10 — Database-backed background execution

**Built:** A new background-run endpoint commits a run and its unique job together. A separate worker polls PostgreSQL, claims one job with `SKIP LOCKED`, obtains a lease token, advances one state, then requeues, pauses, or finishes the job. It renews a 60-second lease every 10 seconds during work and stops accepting new work on `SIGINT`/`SIGTERM` after the current step. A paused approval job is requeued atomically when approval is recorded. The manual `/step` route remains for walkthroughs.

**Files:** `src/app/models.py` maps `RunJobRecord` and its unique/status/index constraints; `migrations/versions/f21c67a4d092_add_run_jobs.py` creates the table. `src/app/jobs/queue.py` owns enqueue, claim, token fencing, heartbeat, step completion, and bounded provider/lease failures. `src/app/jobs/worker.py` runs the poll loop and one agent step per claim. `src/app/agent/factory.py` builds the same engine for the API and worker. `src/app/agent/repository.py` creates a run/job in one transaction and requeues a paused job inside the approval transaction. `src/app/routes/runs.py` exposes background start, job status, and explicit enqueue while preserving manual stepping; `src/app/schemas.py` controls the job response. `tests/test_job_queue.py` covers exclusivity, concurrent claim, lease expiry, heartbeat, bounded failures, and approval gating. `tests/test_worker.py` covers pause/resume, successful execution and verification, transient model timeout, and graceful stop. `docs/background-execution.md` gives the operating commands, state meanings, and crash analysis; `README.md`, `docs/architecture.md`, `docs/failure-model.md`, and `docs/milestone-learning-guide.md` reflect the new path.

**Workflow:** `POST /incidents/{id}/runs/background` → one committed run/job transaction → worker claim with fresh token → load persisted run → execute one allowed agent step and heartbeat → inspect persisted state → requeue if active, pause if approval is needed, or finish if terminal. Human approval commits the decision and makes the paused job eligible again. A crashed worker's lease expires and another worker can continue from persisted state. If it died around a write effect, the M9 execution intent either supplies the saved result or makes the outcome uncertain without issuing the write twice.

**Explain:** Why the HTTP request returns before the run finishes; why a database-backed queue is enough for this workload; what `SKIP LOCKED`, a lease, heartbeat, and token fencing each do; why lease expiry permits at-least-once step delivery but cannot prove a worker died; why decision-provider errors can be retried but an uncertain write cannot; why approval pauses the job; what happens on graceful shutdown and after three dead-worker leases.

**Verification/limits at this stage:** PostgreSQL migration applied; 183 tests passed, 1 opt-in live Gemini test skipped; Ruff, mypy, and `alembic check` passed. At the M10 stage, the queue had no fleet-wide concurrency budget, broker, distributed trace, automatic operator reconciliation, or real-provider idempotency; M11 adds trace propagation through the job. One worker handles one job at a time; multiple processes can claim different rows. An unexpected error fails the job for inspection, and repeated lease deaths stop after three. A run may retain its last persisted state while its job is failed, so both must be inspected. The simulator remains local process-memory state reconstructed only from committed synthetic results.

## Milestone 11 — Structured logs, metrics, and traces

**Built:** Application-owned events are JSON with allowlisted context fields. Prometheus counters, histograms, and a PostgreSQL-backed active-run gauge are available through the API and, when configured, a separate worker metrics port. OpenTelemetry spans cover HTTP requests, agent steps, policy decisions, model calls, tool calls, approvals, and persistence. New background jobs store only W3C `traceparent`; a worker extracts it so its spans are connected to the creation request. An OTLP HTTP collector endpoint is optional. A Grafana dashboard and a host-local Prometheus scrape example are included.

**Files and purpose:** `src/app/observability/logging.py` binds `run_id`, `incident_id`, `step_id`, `tool_name`, and `model_name` through context variables, emits allowlisted JSON events, and adds the active trace ID. `metrics.py` defines run/model/tool/approval/policy/HTTP measures and reads `active_runs` from PostgreSQL at scrape time. `tracing.py` configures the OpenTelemetry provider and optional OTLP exporter. `http.py` extracts incoming trace context, records route-template/status metrics, adds `X-Trace-ID`, and serves `/metrics`. `src/app/main.py` installs those API hooks. `src/app/agent/engine.py` records run-step events, approval-wait events, terminal metrics, and step/transition spans; `repository.py` counts committed run creation and approval denials, records terminal denial, injects job trace context, and traces the write-intent/result persistence methods. `providers/gemini.py` records model duration/tokens/errors and emits model logs without prompts or raw responses. `src/app/policy.py` counts and traces denials; `src/app/tools/executor.py` counts and traces tool attempts, failures, and duration without logging arguments. `src/app/routes/approvals.py` traces and logs a reviewed decision without the approval key. `src/app/jobs/queue.py` injects trace context for separately enqueued jobs; `worker.py` extracts it, wraps each job in a span, emits JSON failure events, and optionally serves metrics on its own port. `src/app/models.py` and `migrations/versions/68d4f7a92731_add_job_trace_context.py` add a nullable `traceparent` column. `pyproject.toml`/`uv.lock` pin the OpenTelemetry and Prometheus-client dependency graph; `.env.example` lists collector and worker metrics settings. `ops/prometheus/prometheus.yml` and `ops/grafana/operations-agent.json` are local scrape and dashboard assets. `tests/test_observability.py` verifies context, metric labels and counters, model token accounting, key exclusion, and the API-to-worker parent/child trace. `docs/observability.md`, `README.md`, `docs/architecture.md`, `docs/background-execution.md`, and `docs/milestone-learning-guide.md` explain operation and boundaries.

**Workflow:** HTTP middleware extracts or creates a trace, records route-template metrics, and returns a trace ID → background-run request saves `traceparent` with its job → worker extracts it and starts a child span → `AgentEngine.step` adds run/incident/step context and nests policy, model, tool, and persistence spans → allowlisted JSON events provide per-run detail → API and worker Prometheus endpoints expose low-cardinality aggregates → Grafana queries both targets. Approval requests become an event and a pause, not a minutes-long open span; a later approval request is a separate HTTP trace linked operationally by run ID.

**Explain:** A database audit step is durable evidence of a committed transition, whereas a log, metric, or exported span can be lost or reset. Logs answer what happened for a particular run; metrics answer how often/slowly across runs; traces show the causal and timing path. `trace_id` and run IDs can be high-cardinality in logs/traces, but putting them on metrics would create an unbounded time series per run. p50 is median latency; p95/p99 describe slow tails, and histogram quantiles are estimates. Worker metrics must be scraped separately from API metrics, while `active_runs` is a duplicated database-backed gauge and should be aggregated with `max`, not `sum`. Neither headers, approval keys, prompts, nor raw tool arguments belong in telemetry.

**Verification/limits:** Migration applied; 188 tests passed, 1 opt-in live Gemini test skipped; Ruff, mypy, `alembic check`, and dashboard JSON validation passed. The in-memory exporter test proves trace parentage, but a live OTLP collector, Prometheus server, and Grafana UI were not launched. The sample Prometheus targets assume those processes run on the host. Multiple worker processes need distinct metrics ports, and no Prometheus multiprocess aggregation is configured. Third-party logs are outside the application-owned JSON event contract. Process-local counters can reset on restart; they do not replace the database audit trail. External service tracing, cost metrics, evaluation metrics, and production access control for `/metrics` remain future work.

## Milestone 12 — Evaluation framework (in progress)

**Built so far:** Twenty versioned incident fixtures, an isolated simulator-backed agent runner, objective per-case scoring, aggregate quality/safety metrics, and a JSON command-line report. One case exposed a rollback without enough evidence; the provider and engine now require corroborating evidence. The initial dataset target is met, but root-cause accuracy, model cost, and failure-recovery metrics are not yet measurable in this harness, so the milestone remains in progress.

**Files and purpose:** `evals/scenarios/*.json` are the ground-truth incidents and simulated environments. `src/app/evaluation/scenario.py` validates fixtures, rejects unknown fields and duplicate IDs, and loads a directory in stable order. `runner.py` creates a fresh simulator and default tool registry per case, wraps tool execution and provider decisions to observe calls, advances `AgentEngine`, simulates a local approve/deny/pause decision, and compares observed behavior with expected outcomes. `metrics.py` aggregates pass, resolution, escalation, tool-use, safety, latency, and observed model-use metrics without inventing unavailable measurements. `__main__.py` prints the JSON report. `src/app/tools/simulator.py`, `search_logs.py`, and `defaults.py` now share scenario-specific logs as well as health and deployments. `tests/test_evaluation_scenarios.py` checks dataset and schema integrity; `tests/test_evaluation_runner.py` checks isolation, the formerly unsafe case, and percentile calculation. `docs/evaluation.md` defines the methodology and limits; `README.md` points to the command.

**Workflow:** Load validated JSON → seed health, deployments, and logs in a fresh simulator → construct the existing registry, executor, decision provider, and agent engine → advance legal states → pause or simulate an operator decision at the approval boundary → record each tool attempt and its success → compare the observed state/actions with the scenario's expected outcome → aggregate and print JSON. No database rows or external actions are created by this runner.

**Explain:** A scenario label is not the agent's answer; ground truth and prediction must be separate. Approval authorizes a proposed action but does not prove it is useful. The safety metrics must be read separately from overall pass rate, and a failing safety case should be fixed rather than removed. p95 describes the slow end of the observed local sample, not production latency. `null` means a metric was not measured, not that its value was zero. The deterministic in-memory runner cannot establish model quality, database crash recovery, or production safety by itself.

**Verification and next work:** With local PostgreSQL available, the updated full suite passed: 215 tests passed and one opt-in live Gemini test was skipped. The deterministic baseline is 20/20 passed with no recorded forbidden or unsafe action. The negative case remains in the dataset as a regression test. Add structured root-cause output and injected recovery cases before interpreting the suite as broader agent quality evidence.

## Milestone 13 — Evaluation regression gate

**Built:** A versioned baseline lists the exact reviewed scenario IDs and safety/quality thresholds. The evaluation command can compare its current results with that baseline, exit nonzero on regression, and publish a JSON report in CI. The gate deliberately excludes p95 latency from a hard threshold because short in-process samples are too noisy for a portable timing gate.

**Files and purpose:** `evals/baseline.json` holds the reviewed IDs and thresholds. `src/app/evaluation/gate.py` validates that file and compares current results against it. `__main__.py` adds `--baseline`, includes pass/failure reasons in the report, and sets the exit status. `.github/workflows/ci.yml` runs the gate after tests and uploads `evaluation-report.json` even on failure. `tests/test_evaluation_gate.py` verifies a clean baseline, removal of a case, an unsafe action, and excess tool calls. `src/app/agent/evidence.py`, `decision_provider.py`, and `engine.py` apply the evidence rule exposed by the first baseline; existing approval/crash-recovery fixtures were updated to gather three read results before a rollback. `README.md` and `docs/evaluation.md` describe the workflow.

**Workflow:** CI installs and tests → deterministic evaluator loads the reviewed scenarios → each scenario seeds its own simulator and runs the agent → gate compares scenario IDs, outcome and tool measures, and zero-tolerance safety measures → JSON report is uploaded → process exits nonzero if any threshold is breached.

**Explain:** A baseline prevents a bad case from being deleted to raise the score. Safety has separate zero-tolerance thresholds; a high overall pass rate does not excuse one unsafe action. The gate measures this particular deterministic simulator, not production success, live Gemini behavior, or root-cause accuracy. A change to the scenario set requires an explicit baseline review. Latency needs a larger, controlled performance benchmark before it can support a reliable gate.

## Milestone 14 — Fault-profile simulator (in progress)

**Built so far:** The simulator models nine named service states, a small dependency graph, synthetic metrics, and ten fault kinds. Injecting database or payment-service failure also degrades the dependent checkout API and emits related error logs. A simulated rollback only heals a bad-deployment fault; an unrelated active deployment can be rolled back without curing the real database fault. The 20-case evaluation set now includes every profile and two adversarial evidence cases. These are fixed profiles, not a time-evolving production-like environment.

**Files and purpose:** `src/app/tools/simulator.py` owns service health, metrics, dependencies, deployments, logs, fault injection, and simulated recovery behavior. `src/app/evaluation/scenario.py` validates optional fault fixtures and `runner.py` applies them after explicit state seeding. `evals/scenarios/09-*.json` through `20-*.json` contain the additional reviewed cases, while `evals/baseline.json` pins all 20 IDs. `tests/test_simulator_faults.py` tests cross-signal consistency, a bad-deployment rollback, an unrelated fault that remains degraded, invalid input, a false alarm, and log-tool visibility. `tests/test_evaluation_scenarios.py`, `test_evaluation_runner.py`, and `test_evaluation_gate.py` enforce the expanded suite.

## Milestone 15 — Security pass (in progress)

**Built so far:** Incident descriptions are bounded at 4,000 characters on create and update. An optional shared `API_ACCESS_KEY` protects `/incidents`, `/runs`, and `/metrics`; the separate approval key continues to protect approval decisions. The threat model lists assets, trust boundaries, mitigations, and residual risks without calling the system enterprise-secure.

**Files and purpose:** `src/app/security.py` checks the configured key with a constant-time comparison and identifies protected route roots; `src/app/main.py` installs it; `src/app/schemas.py` applies the description limits; `.env.example` names the setting. `tests/test_security.py` checks path scope, missing/wrong/correct keys, public health, and oversized create/update requests. `docs/security.md` records the threat model, deployment cautions, and remaining gaps; `README.md` links to it.

**Workflow:** Request enters middleware → protected route requires `X-API-Key` when `API_ACCESS_KEY` is configured → Pydantic rejects oversized incident text before database access → existing route, policy, approval, and tool boundaries continue to apply. Approval uses its own key and durable per-action record. The middleware does not inspect or trust model output.

**Explain:** A shared key is not user identity; input validation is not authorization; an authenticated operator approval still does not justify an unsupported rollback; a prompt-injection string in a log remains untrusted data. The key is optional for localhost development, so network exposure without it is unsafe. Public API docs and health paths, missing rate limits and dependency scanning, and no tenant isolation remain known gaps.

## Milestone 16 — Performance baseline (in progress)

**Built so far:** A read-only benchmark measures serial in-process HTTP health, a deterministic agent escalation, pooled PostgreSQL `SELECT 1`, and HTTP readiness. ## Milestone 18 — LangGraph runtime comparison (isolated experiment)

**Built:** A separate graph reproduces the synthetic bad-deployment path with read evidence, server-owned policy, an approval interrupt, simulated rollback, and verification. The API still uses the custom engine. The graph uses an in-memory checkpointer, so it does not claim parity with PostgreSQL approval, side-effect, or background-job durability.

**Files and purpose:** `src/app/experiments/langgraph_workflow.py` builds the `StateGraph` and keeps the experiment outside the API route/factory. `tests/test_langgraph_experiment.py` covers pause before write, approval/resume, denial, and insufficient evidence. `pyproject.toml`/`uv.lock` add an optional `experiment` dependency group; `.github/workflows/ci.yml` installs it for test coverage. `docs/runtime-comparison.md` contrasts state, checkpoints, write safety, and worker ownership with official reference links; `README.md` links to the comparison.

**Workflow:** Build graph around a fresh simulator → run gather and plan nodes → `interrupt()` pauses the review node with an in-memory checkpoint → `Command(resume=True|False)` restarts that node and either executes/validates the simulated write or escalates. The policy and tool executor are reused, but no persistent approval record or execution-intent row is created by this graph.

**Explain:** A framework can simplify orchestration and pause/resume without providing application-specific authorization or exactly-once external side effects. The interrupt node re-executes from its start, so no write may happen before the interrupt. In-memory checkpoints disappear on process exit; a PostgreSQL-backed checkpointer and crash-window tests would be needed before claiming process-durable equivalence. No migration is justified by this small experiment alone.

## Optional Milestone 23 — Local Compose deployment (cloud pending)

**Built:** One locked Python Dockerfile is used by a migration job, API, and background worker. PostgreSQL health gates the migration; successful migration gates both long-running services. Host ports bind to loopback. The build context and resulting images exclude local `.env`, Git history, tests, and development dependencies. This is a local deployment path, not a cloud rollout.

**Files and flow:** `Dockerfile` copies `pyproject.toml` and `uv.lock`, installs locked runtime dependencies, then copies `src/`, `migrations/`, and `alembic.ini`; `.dockerignore` keeps local secrets and tooling out of the build context. `docker-compose.yml` starts PostgreSQL with its named volume, runs `alembic upgrade head` once, then starts Uvicorn and `app.jobs.worker` against the container-network database URL. `docs/deployment.md` covers startup, logs, stop, and release risks; `README.md` links the path. The API readiness healthcheck probes PostgreSQL; the worker's progress remains visible through queue state and logs.

**Explain:** An image is immutable application packaging, whereas containers are running instances; `postgres` is resolvable on the Compose network while `localhost` inside an app container is not the database; migrations should complete before serving traffic; readiness is different from a process merely existing; a persistent volume is not a backup; `docker compose down` preserves it but `down -v` destroys it. A rolled-back image does not roll back a schema change.

**Verification and limits:** `docker compose config --quiet` passed; all three service images built; an isolated API container returned `/ready` 200 against existing PostgreSQL; the one-shot migration command ran successfully. A temporary worker container started and processed 102 previously queued local development jobs, writing 580 run steps, before being stopped. This changed the local database; no records were deleted or reset. `compose.smoke.yml` now provides a separate empty database and volume: its full stack reached healthy readiness with zero jobs and was removed afterward. CI repeats that isolated test. There is no cloud target, managed database, TLS termination, secret store, registry/publish job, or Kubernetes configuration. Shared API/approval keys and fixed development DB credentials are unsuitable for a public service.
